# Lecture 12 — Agentic AI, Tokens, Pinecone & RAG

## 1. Agentic AI

Agentic AI refers to AI systems that can work toward a goal by using tools, making decisions, and completing multi-step tasks. An agent can receive information, decide what it needs to do, use a connected tool or service, and return a result.

In n8n, AI-related nodes can be connected with tools such as Gmail, databases, and vector stores to build practical automated systems.

---

## 2. Tokens

AI models process text as **tokens**, not as complete words or characters. A token can be a word, part of a word, punctuation, or whitespace.

The classroom rule of thumb that about four English characters equal one token is useful for a quick estimate, but it is not exact. Token counts vary by language, writing style, punctuation, and the model's tokenizer.

Token usage can include:

- **Input tokens:** Instructions, questions, and document context sent to the model.
- **Output tokens:** The answer generated by the model.

Model providers usually charge based on the number of input and output tokens, so sending unnecessarily large documents or prompts can increase cost.

---

## 3. Pinecone and Vector Databases

Pinecone is a vector database. Instead of storing only exact text matches, it stores numerical representations of text called **embeddings**.

Embeddings make it possible to search for text with similar meaning. For example, a question phrased differently from the document can still retrieve the most relevant information.

```text
Document text
  ↓
Embedding model converts text to vectors
  ↓
Vectors stored in Pinecone
  ↓
User question converted to a vector
  ↓
Pinecone returns similar document chunks
```

---

## 4. RAG

RAG means **Retrieval-Augmented Generation**. It combines search with an LLM:

1. Store document chunks and embeddings in a vector database.
2. Receive a question.
3. Retrieve the most relevant chunks.
4. Give those chunks to an LLM as context.
5. Ask the model to answer only from that context.

This reduces hallucination because the model is instructed to use the uploaded documents instead of general knowledge.

---

## 5. Why Documents Are Chunked

A full PDF can be too large or contain many unrelated sections. Chunking divides the extracted text into smaller pieces before creating embeddings. This improves search relevance and keeps the context sent to the LLM manageable.

The supplied ingestion workflow uses a **Recursive Character Text Splitter** with:

- Chunk size: `1000` characters
- Chunk overlap: `200` characters

The overlap helps preserve meaning at the boundary between two chunks.

## 6. Workflow 1: Document Ingestion

The first supplied workflow is [document-ingestion-workflow.json](workflows/document-ingestion-workflow.json). It accepts Gmail attachments and indexes supported documents in Pinecone.

```text
Gmail email with attachment
  ↓
Split attachments
  ↓
Skip previously processed documents
  ↓
Route by file type
  ↓
Extract or load document text
  ↓
Chunk text
  ↓
Create embeddings
  ↓
Insert vectors into Pinecone
  ↓
Reply to confirm ingestion
```

Supported input formats are PDF, TXT, and DOCX. Other attachment types are skipped.

The workflow uses the Pinecone index `n8n-document-rag`, namespace `documents`, and OpenAI's `text-embedding-3-large` embeddings with dimension `3072`. The Pinecone index must be created with compatible settings before the workflow runs.

## 7. Workflow 2: Document Q&A

The second supplied workflow is [document-qa-workflow.json](workflows/document-qa-workflow.json). It receives a new email question, retrieves relevant Pinecone chunks, and replies through Gmail.

```text
Email question
  ↓
Extract question text
  ↓
Validate it is a new question
  ↓
Embed the question
  ↓
Pinecone similarity search (top 5)
  ↓
Build context from returned chunks
  ↓
Groq generates a context-only answer
  ↓
Reply by email
```

The question trigger looks for email subjects containing `question` without attachments. Replies beginning with `Re:` are ignored to avoid an email loop.

The workflow tells the Groq model to answer only from retrieved context. If the question is unrelated, it uses this response:

```text
Your question appears to be unrelated to the uploaded documents. I can only assist with questions based on the information available in the provided documents.
```

If it is related but the answer cannot be found, it returns a different message explaining that the documents do not contain sufficient information.
